# South32 Spillage Audit Report V0.1 — Review Pass 01

## Review Basis
- Working report: `Report-Working/SpillageReport/South32_Spillage_Audit_Report_July2026_S32WPPSR_01_V0.1.docx`
- Context source: `Context/Running_Report_Contextual_Spillage_NotesV3.7.docx`
- Evidence register: `Report-Working/evidence_index.md`
- Visual-review records: Batches A-F
- Scope: first engineering/content/layout review before recommendation expansion and final visual styling.

## Key Review Conclusion
The V0.1 report is a sound engineering-content baseline, but the current Section 16 layout is over-paginated and the evidence selection was too aggressive for this project. The 197 media files in the repository were already pre-filtered by the inspector from a source pool of more than 700 media items. They must therefore be treated as a curated evidence set, not as a raw evidence pool from which only a small minority should automatically survive into the report.

The next pass should prioritise preservation of the intended evidence story while redesigning Section 16 so more photographs can be carried without proportionally increasing page count.

## 1. Evidence Selection Strategy — Revised
The current `evidence_index.md` first-draft candidates remain useful as the strongest or anchor images, but they must not be treated as a final inclusion list.

Recommended working classification for every evidence item:
- **E — Essential body evidence:** required to prove the finding or principal mechanism.
- **S — Supporting/story evidence:** adds unique topology, sequence, extent, operating context, comparison or consequence and should normally remain in Section 16 where it materially improves understanding.
- **A — Appendix/reference evidence:** useful record evidence that does not need to interrupt the main technical narrative.
- **X — Exclude from report:** genuinely duplicative, weak, blurred, or does not add a unique technical point. The repository original remains retained.

The inspector/user should primarily identify **X** items and any items that must be promoted to **E**. This is more appropriate than asking the inspector to rebuild the inclusion list from zero.

## 2. Section 16 Layout — Main Formatting Issue
The present draft contains 92 pages, 50 embedded figures, 156 tables and 77 explicit manual page breaks. Of those page breaks, 73 occur inside Section 16 and force nearly every asset summary and every individual photo evidence sheet onto a new page.

A private layout experiment removed those Section 16 forced page breaks only. The document fell from 92 pages to 63 pages — a reduction of 29 pages / approximately 31.5% — without removing any of the 50 existing images. The experiment was not a valid final layout because some evidence tables split badly across pages, but it proves that the high page count is primarily a pagination/layout issue rather than an unavoidable consequence of the evidence volume.

This supports the inspector's expectation that approximately 30-40% of the current page count can be recovered through proper layout engineering.

## 3. Proposed Section 16 Evidence-Sheet Architecture
Retain the ISS / sheave-report Photographic Evidence Sheet look and discipline, but move from **one photograph = one page** to **one technical story/finding = one evidence sheet or short evidence sequence**.

### 3.1 Asset Summary
The asset heading and finding summary should normally flow directly into the first photographic evidence sheet rather than occupying a separate page.

Add a dedicated row where useful:
- `System context / topology / process relationship`

Use this row selectively where geometry or process position is important to interpretation, for example W10 tunnel access, screens/chutes, L1 tunnel, Sample Conveyors, UC05-UC01, U4 Tripper Car and U5A/U5B.

### 3.2 Multi-photo Evidence Sheets
For evidence supporting the same technical point:
- use one full-width hero image plus one or two supporting/context images; or
- use two portrait images side-by-side; or
- use two related landscape images stacked on one page; or
- use a 2 x 2 photo grid where four context/sequence images are needed and image detail remains legible.

Each image retains its canonical evidence ID and caption.

### 3.3 Reduce Repeated Metadata
The current sheet repeats Finding ID, Asset and July 2026 date on every individual photo. Where several photos belong to one finding/evidence sheet, move shared fields to a single sheet-level metadata bar and retain only photo-specific fields beside/below each image:
- Photo ID
- Component / location
- View / direction
- Caption

This preserves traceability while recovering usable page area.

### 3.4 Assessment Table
Retain the familiar three-part sheave-report logic:
- Observation
- Engineering Assessment
- Recommended Action

But apply it to the **evidence group / technical story** where appropriate rather than repeating substantially the same assessment after every photograph.

For complex findings, split into deliberate sub-stories instead of one oversized sheet. Examples:
- Screens: (1) water escape, (2) corrosion, (3) cut/damaged supports.
- L1: (1) belt-contact evidence, (2) concrete deterioration, (3) steel section loss/corrosion.
- CV09: (1) cleaner geometry/condition, (2) wet-spillage consequence, (3) active operational fallout.
- Sample Conveyor 3: (1) mistracking, (2) product size versus belt width, (3) accumulated containment loss.
- U4: (1) belt mistracking, (2) one-side product loss, (3) U4-specific cleaner geometry.

## 4. Image Orientation / White-space Opportunities
The present report includes multiple portrait images inserted at approximately 1.47 x 3.10 in. These images are technically legible but occupy a very narrow central strip and leave large blank regions on the page. Portrait evidence should normally be paired side-by-side with another portrait/context image or used next to a short assessment block.

Landscape images are commonly inserted at approximately 6.25 x 2.95 in. They are well-sized for detail but currently often occupy a dedicated page with only the metadata and assessment table. Two related landscape photographs can often share one page if the sheet is redesigned around the technical story rather than the individual photograph.

## 5. Story / Topology Requirement
The next evidence pass should identify not only whether a photograph proves a defect, but what role it plays in the report narrative. Suggested story-role tags:
- `TOPOLOGY / ORIENTATION`
- `PROCESS RELATIONSHIP`
- `MECHANISM`
- `DEFECT / CONDITION`
- `EXTENT / SEVERITY`
- `CONSEQUENCE`
- `COMPARATOR / CLEAN CONDITION`
- `OPERATING CONTEXT`
- `MAINTENANCE / DESIGN DETAIL`
- `REMEDIAL-CONCEPT CONTEXT`

This is especially important because the report covers the conveyor/material-handling system from the underground crusher through to the surface/loading station, not a single isolated machine.

## 6. Content Review Observations
### Strong current features
- Cover page is clean and should be retained as the visual anchor.
- Executive summary and dashboard establish the multi-mechanism nature of the audit well.
- Inspection limitations and evidence qualification are technically disciplined.
- Section 16 finding summaries generally preserve direct evidence versus interpretation correctly.
- Section 19 separates confirmed mechanisms from probable/working causes appropriately.
- Section 20 recommendations are logically linked to the current evidence base.

### Items to refine during later content passes
- Expand selected asset narratives with topology/process context where this changes interpretation.
- Remove unnecessary repetition between the asset summary, photo caption, observation and engineering-assessment text.
- Revisit the Appendix A wording that presently assumes further figure reduction; the new approach should record body/supporting/appendix/exclude status instead.
- Preserve clean-comparator images such as CV03/L2 where they materially demonstrate that the audit did not classify every asset as a spillage problem, but avoid allocating excessive space to them.
- Keep current engineering qualifications unchanged unless additional measurements or user-supplied operational information close the gap.

## 7. Formatting / Styling — Defer Until Content Architecture Stabilises
The final styling pass should occur after the Section 16 evidence architecture and image set are stabilised. Planned styling work can then include:
- refined colour palette distinct from, but comparable in polish to, the sheave reports;
- consistent heading hierarchy and spacing;
- improved metadata bars and evidence tables;
- controlled table shading and border weights;
- improved caption hierarchy;
- automatic TOC / List of Figures / List of Tables;
- consistent figure numbering and internal cross-references;
- final header/footer and issue-status treatment.

Do not spend significant time polishing the current one-photo-per-page layout because much of that layout should be structurally replaced first.

## 8. Recommended Immediate Work Sequence
1. **Freeze V0.1 as the baseline** in `Report-Working/SpillageReport/`.
2. Build a media inclusion/story matrix from all 197 evidence items using E / S / A / X plus story-role tags.
3. Inspector/user reviews that matrix, primarily marking definite exclusions and required/promoted evidence.
4. Redesign one complex Section 16 asset as a prototype multi-photo evidence module — recommended first prototype: **Screens**, **CV09**, or **Sample Conveyor 3**.
5. Render the prototype and agree the evidence density/readability standard.
6. Apply the approved module style across all 23 asset groups.
7. Expand the asset-specific narrative / global recommendations once the intended supporting photos are restored.
8. Complete document-wide formatting, colour scheme, automated registers and issue-control polish.

## Working Principle Going Forward
**Do not optimise for minimum page count. Optimise for a complete, defensible engineering story with efficient page use.** A whole-mine material-handling audit can legitimately be a substantial report. Page count should be reduced by removing redundant layout and duplicated content, not by discarding evidence that adds a unique technical point.
